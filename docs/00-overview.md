## 一、这份作品集想解决什么问题

战斗策划岗的作品集，绝大多数是一份**设计文档**。

但设计文档有一个致命弱点：**它无法被证伪**。写得再漂亮，面试官也没法知道那套帧数据跑起来是不是那个手感、那套数值是不是真的平衡、作者是不是根本不知道自己在哪一步想错了。

所以我没有只交文档。我用三件**互相咬合**的产物来回答面试官真正想问的三个问题：

| 面试官真正想问的 | 我的回答工具 | 产物 |
|---|---|---|
| "你的帧数据跑起来是这个手感吗？" | **可玩原型** | 单文件 HTML，双击即玩，60FPS 帧精确 |
| "你说平衡就平衡？" | **蒙特卡洛仿真** | Python 脚本 + 数万局对局数据 |
| "你知道自己哪里错了吗？" | **设计复盘 + 仿真发现** | 白皮书 §6、仿真报告 §5 |

三者的关系是：**文档定义数值 → 原型实现数值 → 仿真检验数值**。任何一处的数字对不上，整个作品集就崩了。所以我做的第一件事是让三者**共用同一套数据**，第二件事是**用脚本自动核验它们是否一致**（见下）。

如果时间有限，只看这三件：

### 2️⃣ 看仿真报告 §5：**三次被数据推翻的设计**

我在白皮书里写死了一条设计原则：

> **"相克关系必须是可被观察的，否则博弈退化为运气。"**（§2.2）

然后我给「影梭」设计了 **3 帧起手（50ms）** 的轻击。

仿真跑出来：**影梭 93.7% 胜率，碾压全场。**

原因很讽刺——**3 帧起手在物理上不可能被反应**（人类简单视觉反应时约 200ms / 12 帧），所以影梭的攻击**无法被防御**。我自己的设计原则，把我自己的英雄设计判了死刑。

**但这不是唯一一次。仿真一共推翻了我三次：**

| # | 被推翻的东西 | 数据说了什么 | 我改成了什么 |
|---|---|---|---|
| 1 | **影梭的 3 帧起手** | 93.7% 胜率 | 改 5 帧起手，回落到 49.1% |
| 2 | **「困兽之斗」整套补偿机制** | A/B 实测只挽回 **1.0pp**，等于失效 | 查清根因（在 1.5 次/局的弹反上），改为**连续型防守补偿**，提升到 **1.9pp** |
| 3 | **横驱的"后跳 220px + 冲击 180px"** | 实装测试打出 `敌人掉血 0` | 后跳改 160px、半径改 240px——**后跳距离大于冲击半径时，AOE 永远打不中** |

> **这是我最想在面试里聊的一件事**：不是"我设计了什么"，而是"**数据告诉我我错了，我改了三次**"。
>
> 第 2 条尤其值得展开：我原本以为机制失效是因为"补偿强度不够"，于是把弹反窗口从 8f 加到 14f、杀势从 +22 提到 +30——**结果只从 1.0pp 变成 0.6pp**。真正去数事件频次才发现，弹反每局只发生 **1.5 次**。
>
> **一个建立在低频事件上的机制，效果上限由事件频次决定，而不是由补偿强度决定。**

### 3️⃣ 看仿真报告 §4：**四条自己在实现里埋的 bug**

仿真不只是验数值，它顺手抓出了四个**真 bug** —— 而且是那种"能玩、但错了"的 bug：

| # | Bug | 后果 | 为什么危险 |
|---|---|---|---|
| 1 | **霸体只画了圈，从未参与判定** | 重锋的核心机制完全失效（胜率仅 16.8%） | 视觉上有反馈，玩起来"感觉有霸体"，但代码里根本没用 |
| 2 | **命中结算按固定顺序执行** | 同帧交换时**先结算的一方永远白赢** | 矩阵不对称：`执锐 vs 影梭` 73.6% + `影梭 vs 执锐` 38.0% = **111.6%** ≠ 100% |
| 3 | **AI 把"靠近"算成了反方向** | AI 跑到墙角不动 | 表面现象是"AI 好菜"，根因是一个符号写反 |
| 4 | **顿帧期间玩家输入被整个丢弃** | 50~200ms 内按的键全部无效 | 经典的"**我明明按了但没反应**" |

> 这四条都是**只有跑数据才会暴露**的问题。策划写文档不会发现它们，做 Demo 摆拍也不会发现它们。
>
> 第 4 条还有个额外故事：它是我在读子任务交付的《打击感与表现规范》时发现的——**那份文档在讲"输入缓冲计时器的时钟错位陷阱"，我回头查自己的代码，发现自己踩了更严重的一个版本。**

| 项目 | 状态 | 说明 |
|---|---|---|
| **落后 60 杀势时胜率 35%~42%** | ⚠️ **单点未达标（43.7%）** | 但**完整的杀势价值曲线达标**：均势 52.6% → 压制 48.2% → 掌控 44.2% → 碾压 40.2%，每档约 4pp、全区间 −12.4pp。评估口径已改为"曲线单调性 + 每档梯度 + 全区间幅度"（详见仿真报告 §6.3） |
| **3v3 团队层** | ❌ **未实现** | 仅有设计草案（白皮书 §10、技能集 §5）。集火、援护、换人全部未验证 |

## 六、一致性核验（可复现）

作品集最重要的纪律是：**文档、原型、仿真三者的数字必须一致**。为此我写了两个自动核验脚本：

**① 原型端**（打开原型后按 F12，粘贴 `prototype/verify-consistency.js` 运行）

核验 4 职业 ×（6 招式 × 6 字段 + 5 招式 × 2 有利帧 + 2 技能 × 4 帧）= **216 个字段**

**② 仿真端**（命令行）

```bash
cd 仿真
python verify.py          # 核验 240 个字段（含职业级参数）
python combat_balance_sim.py --quick   # 快速跑一轮平衡仿真（约 12 秒）
```

**核验结果：原型 216 项 ✅ / 仿真 240 项 ✅，全部一致。抢帧顺序（影梭 5f > 执锐 6f > 长策 8f > 重锋 10f）亦一致。**
