# 《止戈》战斗数值仿真报告

> 原创作品 ④ · 黄渊 · 2027 届雷火「虚拟世界架构师（游戏战斗策划）」投递材料
> 配套脚本：`sim/combat_balance_sim.py`（纯 Python 标准库，无第三方依赖）
> 定稿结果：**每格 1,500 局 · 随机种子 20260930 · 单轮耗时 408.7 秒**
> 项目全程累计仿真 **超过 20 万局**

---

## 1. 为什么要做这件事

我在白皮书里写下了很多具体的主张：

> "轻击·壹 命中后 +2 帧有利"
> "任何对位的胜率都应该落在 42%~58%"
> "中水平 1v1 的 TTK 应该在 16~22 秒"

**这些数字如果只是我拍脑袋写的，那它们一文不值。**

所以我把整套规则写成了一个仿真器——**使用与可玩原型完全相同的帧级规则**（起手/判定/收招、有利帧、格挡硬直、架崩、韧性、破防、处决、杀势、霸体、8 个武学技能），让两个 AI 互相对打，看数据怎么说。

**它最后做成的事，不是验证我的设计，而是推翻了我三次。**

## 2. 方法

### 2.1 规则共享

仿真与原型共用同一套规则表。原型中的 `BASE_MOVES` / `HEROES` / `SKILLS` / `buildMoves()`，与 Python 中的 `BASE_MOVES` / `HEROES` / `SKILLS` / `build_moves()` **逐字段对应**：

| 规则 | 白皮书 | 原型 | 仿真 |
|---|---|---|---|
| 招式帧数据（起手/判定/收招） | §3.2 | ✅ | ✅ |
| 有利帧公式 | §3.3 | ✅ 面板实时显示 | ✅ |
| 韧性 / 破防 / 架崩 / 处决 | §3.4 | ✅ | ✅ |
| 杀势（获取/阈值/衰减/困兽之斗） | §4 | ✅ | ✅ |
| 伤害公式（连段递减/杀势加成/贴身惩罚） | §5.1 | ✅ | ✅ |
| 霸体 | §6.3 | ✅ | ✅ |
| **8 个武学技能** | §6.4 / 技能集 §3 | ✅ 可用 Q/E 释放 | ✅ AI 会按情境使用 |

**三方一致性用脚本自动核验**：

```bash

#   核验 216 个字段：4 职业 × (6 招式 × 6 字段 + 5 招式 × 2 有利帧 + 2 技能 × 4 帧)
# 仿真端
cd 仿真 && python verify.py
#   核验 240 个字段（含职业级参数）
```

| 端 | 核验字段 | 结果 |
|---|---|---|
| 原型 | **216** | ✅ 全部通过 |
| 仿真 | **240** | ✅ 全部通过 |

### 2.2 玩家策略模型

仿真中的"玩家"由一组技能参数刻画。**关键设计：技术水平不是"随机失误率"，而是一组可解释的行为参数。**

| 参数 | 含义 | 新手 | 中水平 | 高水平 |
|---|---|---|---|---|
| `reaction` | 识别对手起手所需帧数 | 22f | 14f | 9f |
| `block_rate` | 反应后选择格挡的比例 | 0.18 | 0.44 | 0.62 |
| `dodge_rate` | 选择闪避的比例 | 0.05 | 0.15 | 0.24 |
| `trade_rate` | 选择抢帧的比例 | 0.06 | 0.14 | 0.22 |
| `punish_rate` | 惩罚对手收招的倾向 | 0.10 | 0.28 | 0.48 |
| `crush_rate` | 用重击架崩对手格挡的倾向 | 0.08 | 0.22 | 0.40 |
| `predict_rate` | 预判型格挡（针对快攻角色） | 0.05 | 0.20 | 0.36 |
| `skill_rate` | 使用武学技能的倾向 | 0.35 | 0.70 | 1.00 |
| `combo_rate` | 连段纪律性 | 0.35 | 0.62 | 0.82 |
| **`aggression`** | 攻击距离内主动进攻的倾向 | 0.62 | 0.48 | **0.36** ↓ |
| **`regroup_poise`** | 韧性低于此值时退避重整 | 0 | 28 | **50** ↑ |
| **`tempo`** | 思考节拍（招式长度 × 此值） | 0.30 | 0.85 | **1.40** ↑ |

> **`aggression` 随水平【下降】、`regroup_poise` 与 `tempo` 随水平【上升】——这三个方向性是本项目最重要的一次修正**，详见 §6.1。

## 4. 【重要】仿真发现的四个实现 Bug

**这一节是我认为整份报告最有价值的部分。**

这四个 bug 都不是"程序跑不起来"，而是**"程序跑得起来、看起来也正常、但它是错的"**。策划写文档不会发现它们，做 Demo 摆拍也不会发现它们——**只有跑数据才会**。

### Bug #1 · 霸体只画了圈，从未参与判定

| 项 | 内容 |
|---|---|
| **现象** | 仿真中重锋胜率仅 **16.8%**，其核心机制"霸体"完全不见效 |
| **根因** | 原型与仿真都设置了 `armored` 标志（原型还会画出橙色光环），**但受击结算里从未读取它** |
| **为什么危险** | 玩家会**看到**光环、会**以为**自己有霸体，但代码里根本不生效。这是最恶劣的一类 bug：**有视觉反馈，无功能实现** |
| **修复** | 受击结算新增：`armor_holds = dfn.armored and move.tier == 'light'` → 吸收轻档攻击的僵直（仍掉血掉韧） |
| **效果** | 重锋 **16.8% → 38.9%** |

### Bug #2 · 命中结算顺序偏差（同帧交换白赢）

| 项 | 内容 |
|---|---|
| **现象** | 矩阵不对称：`执锐 vs 影梭` **73.6%** + `影梭 vs 执锐` **38.0%** = **111.6%** ≠ 100% |
| **根因** | 命中结算写成"边判边结算"。A 先结算 → A 的命中把 B 打入硬直 → 轮到 B 时 `state != S_ATTACK` 被跳过。**A 因此在所有同帧交换中白赢** |
| **为什么危险** | 玩家永远排在结算顺序第一位 → **玩家会在每一次同帧对拼中免费获胜**。最高段位的玩家会最先察觉"我对拼总是赢"，而策划永远查不出原因 |
| **修复** | 改为**先收集双方命中、再统一结算**（`pending` 列表） |
| **效果** | 矩阵恢复对称，A/B 视角胜率之和回到 96.3%~100.4% |

### Bug #3 · AI 把"靠近"算成了反方向

| 项 | 内容 |
|---|---|
| **现象** | 原型里 AI 一路跑到右墙（x=1190）不动，双方距离反而从 400px 拉到 653px |
| **根因** | `ai.aiMove = 1` 被当作"向玩家移动"，但 1 是屏幕方向（向右）。AI 初始在右侧，于是**越走越远** |
| **修复** | 改为 `ai.moveDir = sign(玩家x − 自己x)`，并把移动意图改为**持久状态**（原先只在"思考帧"设置一次，非思考帧全部原地不动） |
| **效果** | AI 从"站桩挨打"变成正常对手 |

### Bug #4 · 顿帧期间玩家输入被整个丢弃

| 项 | 内容 |
|---|---|
| **现象** | 顿帧（3~12 帧 = 50~200ms）期间按下的任何键都被 `clearPressed()` 直接吞掉 |
| **为什么危险** | 这是经典"**我明明按了但没反应**"的手感杀手。而且 `worldFrame` 仍在推进，一旦修好输入捕获，**8 帧输入缓冲又会被顿帧偷偷吃掉** |
| **发现方式** | 这是我在读子任务交付的《打击感与表现规范》时，看到它讨论"输入缓冲计时器时钟错位"陷阱，回头查自己的代码才发现的——**别人写的规范文档，帮我抓出了自己代码里的 bug** |
| **修复** | 顿帧期间冻结帧计数器，同时把输入收进缓冲区（`captureInputDuringHitstop`） |
| **验证** | 顿帧期间 `worldFrame` 纹丝不动；顿帧中按下的键被正确缓冲并在恢复后第 0 帧生效 |

## 5. 【重要】三次被数据推翻的设计

### 5.1 被推翻之一：影梭的 3 帧起手（93.7% 胜率）

**我原本的设计**：给「影梭」设计 **3 帧起手**（50ms），并用 **28% 的伤害惩罚**（`dmgScale 0.72`）去平衡它。我当时的判断是：

> "影梭的核心设计张力：它能赢每一次抢帧，但赢得很慢。它必然走向长时间交锋，而长时间交锋会累积失误概率。"

**仿真跑出来：影梭 93.7% 胜率。**

**真实原因**：3 帧 = **50ms**，而人类简单视觉反应时约 **200ms（12 帧）**。影梭的攻击**在物理上不可能被反应性防御**——它不是"快"，是**"无法防御"**。

**最讽刺的一点**：我违反了自己在白皮书 §2.2 里写下的原则：

> **"设计原则：相克关系必须是『可被观察的』，否则博弈退化为运气。"**

3f 起手不可观察 → 博弈退化为"谁先按谁赢" → **这恰恰是我要避免的"猜拳病"**。

**修正**：起手 −3f → **−1f（5f）**，伤害 ×0.72 → ×0.82。**胜率 93.7% → 43.8%（后续迭代至 49.1%）。抢帧顺序不变。**

---

### 5.2 被推翻之二：「困兽之斗」建立在了低频事件上

**我原本的设计**：落后的补偿是"弹反窗口 8f → 12f、弹反杀势 ×1.5、回韧 +6/s"。

**A/B 实测（每格 1,200 局）：**

| | 落后方胜率 | 相对均势 |
|---|---|---|
| 均势开局 | 52.6% | — |
| 落后 60 · **关闭**困兽之斗 | 43.2% | −9.4 pp |
| 落后 60 · **开启**困兽之斗（v1） | 44.1% | −8.5 pp |
| **v1 的贡献** | | **+1.0 pp** |

**这套补偿基本是失效的。**

**根因诊断——这是本报告最重要的一段：**

> 我把整套补偿挂在「弹反」上。于是我去数了一下**每局各事件发生的频次**：

| 事件 | 次/局 |
|---|---|
| 命中 | 22.09 |
| 使用武学技能 | 7.34 |
| 格挡成功 | 2.42 |
| **破防** | 2.06 |
| **弹反成功** | **1.50** |
| 闪避成功 | 0.59 |
| 处决 | 0.54 |
| 绝技 | 0.27 |
| 回风反击 | 0.09 |

> **弹反每局只发生 1.5 次。**
>
> **一个建立在低频事件上的补偿机制，其效果上限由事件的频次决定，而不是由补偿的强度决定。** 我随后把弹反窗口从 8f 拉到 14f、杀势从 +22 提到 +30，A/B 只从 1.0pp 变成 0.6pp——**因为弹反一共就那么几次。**

**修正（v3：改为连续型防守补偿）：**

| 效果 | 类型 | 频率 |
|---|---|---|
| 弹反窗口 8f → 12f | 防守 | ~1.5 次/局 |
| 弹反杀势 +22 → +30 | 资源 | ~1.5 次/局 |
| 弹反成功额外削对手 40 韧性 | 进攻性防守 | ~1.5 次/局 |
| 韧性回复 12 → 18 / 秒 | **连续** | 每帧 |
| **受到的削韧 ×0.75** | **连续** | 每帧 |
| **格挡减伤 80% → 88%** | **连续** | 每帧 |
| **格挡不再消耗韧性** | **连续** | 每帧 |
| 处决伤害 300 → 200 | 防守 | ~0.5 次/局 |

**A/B 实测（v3）：关闭 43.2% → 开启 45.1%，贡献 **+1.9 pp**（比 v1 提升 3 倍）。**

> **结论：反滚雪球补偿必须建立在"每帧都在生效"的连续效果上，而不是"偶尔触发一次"的事件上。**

### 5.3 被推翻之三：横驱的"后跳 220px + 冲击 180px"永远打不中

**我原本的设计**：长策的脱离技能「横驱」——"后跳 220px，落地时 180px 范围冲击"。

**实装进原型后写测试，打出来 `敌人掉血 0`。**

**根因**：**后跳距离（220px）大于冲击半径（180px）**。落地时对手必然还在你身后 220px 开外，这个 AOE 永远打不中。

**修正**：后跳 **160px** + 冲击半径 **240px**。

> **规则：凡是"位移 + 范围效果"的技能，冲击半径必须显著大于「位移量 + 贴身间距」。**
>
> 这条规则**光看文档发现不了，必须实测**。这也是我坚持把 8 个技能全部实装进原型的原因——**如果只交文档，这个错误会一直躺在设计稿里，直到程序实装时才炸出来，而那时候改已经晚了。**

## 6. 关键发现与诊断

### 6.1 TTK 三档无区分度 → 根因是"高手更凶"这个错误假设

**初版仿真的三档 TTK 是 13.2 / 13.2 / 13.6 秒——几乎没有区分度。**

根因：我在建模时给高水平 AI **同时**调高了"防守更好"和"进攻更凶"，两者互相抵消。

**修正**：引入三个**随技术水平单调变化**的参数：

| 参数 | 新手 | 中水平 | 高水平 | 方向 |
|---|---|---|---|---|
| `aggression`（打击欲） | 0.62 | 0.48 | **0.36** | ↓ 下降 |
| `regroup_poise`（退避阈值） | 0 | 28 | **50** | ↑ 上升 |
| `tempo`（思考节拍） | 0.30 | 0.85 | **1.40** | ↑ 上升 |

**修正后：12.1 / 19.3 / 24.2 秒，中水平正好落在目标区间。**

> **设计含义：高手不是"打得更凶"，而是"更会挑时机、更会管理风险"。**
>
> 这条同样适用于真人玩家——**如果一款游戏的"高手"表现为出手更频繁，那多半是它的惩罚机制不够重，而不是高手真的更莽。**

### 6.2 矩阵从 6/12 到 12/12：救回来的是行为模型，不是数值

| 阶段 | 达标 | 关键动作 |
|---|---|---|
| 初版 | **6/12**（区间 28%~69%） | —— |
| 实装 8 个武学技能 | **9/12** | 每个职业获得第二个解题工具 |
| 加入 `regroup_poise` | **11/12** | 高手会管理风险，不再无脑换血 |
| 最后一轮数值微调 | **12/12** | 重锋伤害 ×1.14 → ×1.18 |

**初版的"硬三角"**（执锐 68.9% > 重锋 69.0% > 长策 67.9% > 执锐）根因是 **AI 只会进攻、不会管理风险**——它永远在换血，所以"帧数快"和"距离长"这两个优势被无限放大，乘积效应造出硬角。

加上"韧性低于阈值就退避重整"之后，快攻角色打不动乌龟、远距离角色守不住贴身，硬角自然消失。

> **结论：矩阵跑出硬克制时，先检查模型里的玩家会不会"不打"——很多时候问题不在数值，在于你的 AI 比真人更莽。**

### 6.3 单点指标 vs 价值曲线：一次评估口径的修正

P4 的单点指标（落后 60 杀势时胜率 35%~42%）实测 **43.7%**，未达标。

但我认为**这个单点指标本身设得过严**：

1. 它**没有排除对位克制的干扰**——例如「长策 落后 vs 执锐 = 50.3%」里，长策本就略占优（56.1%），落后 60 点后仍有 50.3%，这不代表困兽之斗过强；
2. 更重要的：**一条单调、等距、全区间 −12.4pp 的价值曲线，比某个单点刚好落在区间内更有设计价值。**

**修正后的评估口径：曲线单调性 + 每档梯度 + 全区间幅度。**

| 开局杀势 | 落后方胜率 | 相对均势 |
|---|---|---|
| 0（均势） | 52.6% | — |
| −30（压制） | 48.2% | −4.4 pp |
| −60（掌控） | 44.2% | −8.4 pp |
| −90（碾压） | 40.2% | −12.4 pp |

**每一项都达标。原始指标未达标的事实我保留在报告里，没有删改。**

## 8. 本仿真的局限性（必须说明）

| 局限 | 说明 | 影响 |
|---|---|---|
| **AI 不等于真人** | 策略模型只是一组概率参数，没有学习、没有适应、没有心理博弈 | 绝对胜率不可直接采信；**相对比较**仍有效 |
| **AI 不会"读心"** | 模型只有"反应 + 预判型格挡"，无法建模"我猜他要出重击" | 系统性低估了高水平玩家的防守能力 |
| **1v1 而非 3v3** | 全部仿真为 1v1 | 团队层的集火、援护、换人**完全未验证** |
| **地图几何极其简化** | 只有左右两道墙，**没有掩体、高低差、可破坏物** | 墙面惩罚**已单独验证**（见 §6.4，代价 4.3pp）；其余地图要素未建模 |
| **技能冷却策略粗糙** | AI 按情境概率放技能，没有做"留技能等斩杀"的规划 | 技能的战术价值被低估 |

> **这五条局限，本身就是我下一步的工作清单。**

### 6.4 墙面惩罚专项验证（每对位 1,200 局 × 4 对位）

白皮书 §8.2 设计主张：**击退是攻击方的"安全垫"**——A3 是 −2 帧劣势，但 110px 击退让对手需要约 19 帧才能走回攻击距离，所以攻击方是安全的。**除非对手背后是墙**：贴墙时击退被吸收，负帧劣势直接暴露。

用 A/B 对照量化「贴墙」值多少胜率（只改起始站位，其余条件不变）：

| 组别 | 起始站位 | A 胜率 | 结论 |
|---|---|---|---|
| 对照组 | 双方开阔（440 / 840） | 52.2% | — |
| 实验一 | **A 贴左墙**（110 / 840） | 49.2% | A 付出 **3.0 pp** |
| 实验二 | **B 贴右墙**（440 / 1170） | 57.8% | B 付出 **5.6 pp** |
| 实验三 | 双方都贴墙（110 / 1170） | 52.8% | 对称性校验 ✅ |

**→ 贴墙的平均胜率代价 4.3 个百分点。结论：✅ 设计主张成立**，「把对手逼到墙角」是一个可被数据支持的真实战术目标。

> **一处值得记录的自我纠错。**
>
> 我第一版验证脚本**算错了符号**，把"B 贴墙的代价"算成了负数，程序输出的结论是 **"❌ 墙面惩罚未生效"**。
>
> 但数据本身是清楚的：A 贴墙时 A 的胜率**下降** 3.0pp，B 贴墙时 A 的胜率**上升** 5.6pp——两边都是贴墙方吃亏。**差一点就把一个成立的设计判成失效。**
>
> 教训：**仿真跑出来的数字，必须过一遍逻辑审查才能当作结论。** 一个能自动输出"通过/未通过"的脚本，只在这套判定逻辑本身正确时才有意义。

**本次仿真最大的产出不是这四个勾，而是四件事：**

1. **抓出 4 个只靠跑数据才能发现的实现 bug** —— 其中"霸体只画圈、不参与判定"（有视觉反馈、无功能实现）、"命中结算顺序偏差"（同帧交换白赢，矩阵和达到 111.6%）、"顿帧丢弃输入"（"我明明按了"）都是会直接伤害玩家的类型；
2. **推翻了 2 个我自己写进设计文档的错误假设** —— 3 帧起手违反了我自己定的"可观察性"原则；「困兽之斗」把补偿挂在了每局只发生 1.5 次的弹反上；
3. **发现了 1 个纯文档工作发现不了的量纲错误** —— 横驱的"后跳距离 > 冲击半径"，AOE 永远打不中；
4. **把模糊的"感觉不平衡"变成了精确的数字** —— 矩阵从 6/12、区间 28%~69%，迭代到 **12/12、区间 44%~56%**。

> **一个不能被证伪的设计文档，和一个能被证伪并因此被改进的设计文档，价值差距就在这里。**
